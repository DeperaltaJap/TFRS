# TFRS Changelog — 2026-09-16

## Overview

This document records all changes made to the TFRS (Tricycle Franchise Registration System) codebase on September 16, 2026. The primary goal was to complete the full CRUD (Create, Read, Update, Delete) cycle, fix the model/service data mismatch, remove dead code, and ensure consistency across all controllers, views, and the database.

---

## 1. Database Schema Changes

### 1.1 Added 5 missing columns to MAINTABLE

**File:** `TFRSdb.accdb` (via `ALTER TABLE` SQL)

| Column Added | Type | Reason |
|---|---|---|
| `ContactNo` | TEXT(20) | Model had `ContactNo` property but it was never persisted to the database |
| `CommunityTaxNo` | TEXT(20) | Model had `CommunityTaxNo` property but it was never persisted |
| `PlaceIssued` | TEXT(50) | Model had `PlaceIssued` property but it was never persisted |
| `TypeOfOwnership` | TEXT(30) | Model had `TypeOfOwnership` property but it was never persisted |
| `VerifiedBy` | TEXT(50) | Model had `VerifiedBy` property but it was never persisted |

**Reason:** The `MainTableRecord.cs` model contained 5 properties (`ContactNo`, `CommunityTaxNo`, `PlaceIssued`, `TypeOfOwnership`, `VerifiedBy`) that were present in the form views but never existed in the database. This meant any data entered for these fields was silently dropped when saving. The `MainTableService` SQL queries only had 22 columns, missing these 5. The database `MAINTABLE` table only had 22 columns as a result.

**Action taken:** Executed `ALTER TABLE MAINTABLE ADD COLUMN [ColumnName] [Type]` for each of the 5 missing columns via a C# diagnostic tool using `System.Data.OleDb`. The database now has 27 columns total.

## 2. Service Layer Changes

### 2.1 Updated `IMainTableService.cs`

**File:** `TFRS/Services/IMainTableService.cs`

**Changes:**
- Added `void Update(MainTableRecord record)` method signature
- Added `void Delete(string franchiseNumber)` method signature

**Reason:** The interface previously only had `GetAll()`, `Add()`, and `GetByFranchiseNumber()`. Update and Delete were completely missing, making full CRUD impossible. Any controller action needing to modify or remove records had no interface to implement.

### 2.2 Rewrote `MainTableService.cs` with full CRUD and all 27 fields

**File:** `TFRS/Services/MainTableService.cs`

**Changes:**

#### 2.2a Added `using System.Linq;` directive
**Reason:** Needed for `.Where()` and `.Select()` LINQ methods in the `Update()` method.

#### 2.2b Added `AllColumns` static array and `ColumnList`
**Reason:** Centralized the list of all 27 column names. Previously, each SQL method (`GetAll`, `Add`, `GetByFranchiseNumber`) had its own hardcoded column list, making it easy to miss fields when updating. Now all methods reference the same `AllColumns` array, ensuring consistency.

#### 2.2c Added `MapReader(OleDbDataReader reader)` private method
**Reason:** Previously, `GetAll()` and `GetByFranchiseNumber()` each had their own inline object initializer mapping `reader[0]`, `reader[1]`, etc. to properties. This positional indexing approach was fragile and error-prone — if the SELECT column order changed, the mapping would break silently. The new `MapReader` method uses named column access (`reader["COLUMN_NAME"]`) and `reader.GetOrdinal("COLUMN_NAME")` for nullable fields, making the mapping robust and readable.

#### 2.2d Rewrote `GetByFranchiseNumber()` to use `MapReader`
**Reason:** Replaced positional `reader[0]`, `reader[1]` indexing with `MapReader()` for consistency and maintainability.

#### 2.2e Rewrote `Add()` to use `ColumnList` and `AddParameters`
**Reason:** Previously had a hardcoded SQL string with 22 columns. Now dynamically generates the column list and placeholders from `AllColumns`, ensuring all 27 fields are included. Extracted parameter addition into a reusable `AddParameters` method.

#### 2.2f Added `Update(MainTableRecord record)` method
**Reason:** This was completely missing. Implemented as a proper UPDATE SQL statement that sets all 27 columns based on the record, using `TRICYCLE_FRANCHISE_NUMBER` as the WHERE clause key. Uses a dedicated parameter indexing approach to ensure correct mapping between the 27 SET parameters and the 1 WHERE parameter (@p28). Added a `GetParamValue` helper method for the switch-based parameter mapping.

#### 2.2g Added `Delete(string franchiseNumber)` method
**Reason:** This was completely missing. Implemented as a simple `DELETE FROM MAINTABLE WHERE [TRICYCLE_FRANCHISE_NUMBER]=?` SQL statement.

#### 2.2h Added `AddParameters` helper method
**Reason:** Extracts the repetitive parameter binding logic (27 `AddWithValue` calls) into a single reusable method. Both `Add()` and `Update()` use this method. Each parameter maps to the correct model property based on its position in `AllColumns`.

#### 2.2i Added `GetParamValue` helper method
**Reason:** The `Update()` method needs the same parameter mapping as `Add()` but must skip the franchise number column (index 1) for the SET clause and use it separately for the WHERE clause. The `GetParamValue` method uses a C# switch expression to map each `AllColumns` index to the correct model property value, providing type-safe and readable parameter extraction.

**File:** `TFRS/Controllers/ApplicationController.cs`

**Reason:** The edit workflow was completely missing. There was no way to load an existing record into the form for editing. This action enables the "Edit" button in the masterlist to navigate to the form pre-populated with the selected record's data.

### 3.3 Added `Edit()` POST action to `ApplicationController`

**File:** `TFRS/Controllers/ApplicationController.cs`

**Change:** Added `[HttpPost] public IActionResult Edit(MainTableRecord model)` that validates the model and calls `_mainTableService.Update(model)`.

**Reason:** The form submission for editing was missing. Without this action, clicking "Update Record" on the edit form would have no backend endpoint to call.

### 3.4 Added `Delete()` POST action to `ApplicationController`

**File:** `TFRS/Controllers/ApplicationController.cs`

**Change:** Added `[HttpPost] public IActionResult Delete(string franchiseNumber)` that calls `_mainTableService.Delete(franchiseNumber)` and redirects to Records index.

## 9. Technical Decisions

### 9.1 Used named column access instead of positional indexing

**Decision:** Replaced `reader[0]`, `reader[1]`, etc. with `reader["COLUMN_NAME"]` and `reader.GetOrdinal("COLUMN_NAME")`.

**Reason:** Positional indexing is fragile — if the SELECT column order changes, the mapping breaks silently. Named access is self-documenting and robust. The `MapReader` method centralizes this mapping in one place.

### 9.2 Used separate `GetParamValue` method for Update instead of reusing `AddParameters`

**Decision:** Created a `GetParamValue` method with a switch expression instead of trying to reuse `AddParameters` for the Update method.

**Reason:** The `AddParameters` method uses sequential `@p1` through `@p27` based on `AllColumns` order. The `Update` method needs to skip the franchise number column (index 1) in the SET clause and use it separately in the WHERE clause. A separate method provides clear parameter indexing control.

### 9.3 Used form action switching instead of separate edit form

**Decision:** Used a single form (`Applicationpage.cshtml`) that switches its action between `Save` and `Edit` based on `ViewBag.IsEditMode`.

**Reason:** Creating a separate edit form would duplicate 674 lines of HTML. Switching the form action is a clean approach that reuses the existing UI while supporting both create and edit workflows.

### 9.4 Used `confirm()` dialog before delete operations

**Decision:** Added `confirm()` dialog before all delete operations.

**Reason:** Delete is a destructive operation. A confirmation dialog prevents accidental data loss. This is a standard UX pattern for destructive actions.

### 9.5 Used inline forms for masterlist delete buttons

**Decision:** Added `<form>` elements inline in the `TFrecords.cshtml` table rows for delete buttons.

**Reason:** This provides a proper POST request for delete operations without requiring JavaScript. The `onsubmit="return confirm(...)"` pattern provides the confirmation dialog. This is the standard ASP.NET MVC pattern for row-level actions in a table.

## 10. Remaining Known Issues (Not Fixed in This Session)

These are acknowledged but not addressed in this session:

1. **Client-side search only** — The search functionality in `Applicationpage.cshtml` and `TFrecords.cshtml` filters data client-side using JavaScript. There is no server-side search endpoint.
2. **Stub controllers** — `AccountController`, `AttendanceController`, `IDSystemController`, `SearchController` remain unimplemented stubs.
3. **Machine-specific database path** — `appsettings.json` still contains the absolute path `C:\ObsVault\JapDev\TFRS\TFRSdb.accdb`. This should be made portable.
4. **`TodaList.cs`** — This is an empty stub model that may be dead weight.
5. **No authentication/authorization** — The `AccountController` is a stub, so there is no login/logout functionality.
6. **Certificate page JavaScript** — The `fetch('/Records/Delete', ...)` call in `certificateRegistration.cshtml` uses `application/x-www-form-urlencoded` content type but the controller action doesn't explicitly validate the content type. This works but could be more robust.
7. **No CSRF protection on inline delete forms** — The `TFrecords.cshtml` inline delete forms don't include `@Html.AntiForgeryToken()`. The `Applicationpage.cshtml` form does include it, but the row-level delete forms don't. This is a security concern if anti-forgery validation is enabled globally.
